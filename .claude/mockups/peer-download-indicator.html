Peer-download indicator — sender side

Proposal: show the owner of a file who is currently downloading it (with avatars) and how far they've got. Click the toggle to flip themes.

Proposal — not yet implemented. New worker plumbing required.

Who is feasible today. Identity (display name + avatar) already lives on space.members[]; MIR-03 cryptographically binds each connection's Noise key to a profileKey. The overlay content-backend serve path (protocol-v2.js → _onChunkNeed) already has the requesting peer, the content hash, and the exact chunk bytes in scope — the clean place to emit a new event:peer-downloading { spaceId, path, peerKey, bytes, total }. The legacy Hyperdrive path needs Hypercore upload listeners + a Noise→profileKey index first. Every state below uses only data the sender already holds.

0 · Today — the owner gets no signal

A file you own currently reads only “Shared by you.” When Alice pulls it from you, nothing changes on your screen. This row is recreated faithfully from FileCard.tsx; the badge is the real Badge primitive.

Annotation: 100% existing UI — shown as the baseline the rest of this mockup adds to.

3 · Expanded — per-peer breakdown (popover)

Expanding the stack reveals one MemberCard-style row per downloader, each with its own progress, speed and ETA. This is where the sender sees exactly who's at what percent. A stalled peer (offline / paused) is shown muted with a “Waiting” note.

Annotation: row layout = MemberCard + ProgressBar primitives. New: per-peer progress data (one entry per peerKey).

4 · Approach B (alternative) — progress ring around each avatar

The most compact option: wrap each downloader's avatar in a circular progress ring (orange = the same secondary-container as the bars). Per-peer progress is legible at a glance with no popover and no horizontal lane — good for dense lists. Trade-off: harder to show speed/ETA inline, and rings get cramped past ~4 peers (then fall back to the stack + chip).

Annotation: the ring is net-new (SVG); avatar + colors are shipped tokens. Presented as a rejected-by-default alternative to Approach A — keep for very dense file lists.

5 · Lifecycle — completion, then back to rest

When a peer finishes, the lane briefly resolves to a confirmation (“Alice has a copy”, green check) for a few seconds, then the row settles back to plain “Shared by you.” No persistent clutter; the indicator only exists while a transfer is live.

Annotation: green = success token (same as “On your device”). Transient by design — avoids leaving stale peer state on the row.

Recommendation

  • Ship Approach A (Sections 1–3): reuses the shipped DownloadProgressLane, avatar stack and MemberCard rows — minimal new UI, scales from one peer to many, and the expand affordance keeps the row uncluttered.
  • Keep Approach B (ring avatars) in reserve for very dense file lists where a horizontal lane doesn't fit.
  • Data source: emit event:peer-downloading from the overlay serve path (_onChunkNeed) — peer, content hash and chunk bytes are already in scope there. The renderer maps peerKey → SpaceMember (already in SpaceView) for the avatar + name. Legacy Hyperdrive shares need Hypercore upload listeners + a Noise→profileKey index as a follow-up.
  • A11y: avatars carry role="img" + name; progress is role="progressbar" with aria-valuenow/valuetext and no aria-live (matches the existing lane); the expand control is a real button with aria-expanded.
