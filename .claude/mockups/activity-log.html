Activity Log — viewer on Account, configuration in Settings

The log viewer hangs off the Account (profile) screen; its configuration lives under Settings. The two are cross-linked with the same nav-card pattern Account already uses for Network Status. Recreated from Account.tsx, Settings.tsx, StorageSettings.tsx and AppearanceSettings.tsx; tokens from design.md. Toggle dark to verify both themes.

Where things live

Account  ──▸ Activity Log (viewer: search · filter · events)   [A → B]
                    │  ▲
      "Log settings" │  │ "Open Activity Log"          ← the two cross-links
                    ▼  │
Settings ──▸ Activity Log (config: recording · retention · export · delete)   [D → E]

Back targets follow the shipped convention in useAppNavigation.ts (where network-status → back → account): the viewer backs out to Account, the config backs out to Settings. A cross-link is a lateral jump — after following one, Back returns to that screen's own parent, not to where you came from.

Recreated from code vs proposed

  • · Recreated: screen shell (h-[calc(100vh-5.5rem-var(--banner-h,0px))] overflow-y-auto scrollbar-thin pb-8 + pt-8 px-8 max-w-2xl mx-auto), PageHeader, SectionHeading, the Account profile/security/network sections and its nav-card button (Account.tsx), the settings-hub row (Settings.tsx), the ACTION_BUTTON class string and border-t border-outline-variant/40 divider (StorageSettings.tsx), the segmented control (AppearanceSettings.tsx), the Toggle switch row and Badge pill shape.
  • · Proposed (new): the Account "Activity" section, the Activity Log viewer, the Activity Log settings screen, the two cross-link cards, the search input, filter-trigger row, active-filter chips, day-grouped list, and three empty states.
  • · Both cross-links reuse Account's Network-Status nav card verbatim — no new primitive, and no header action slot (PageHeader takes only title/subtitle/onBack; adding an action slot would be a real component change and was avoided).

Why the split lands this way

  • · The viewer is about you. It sits beside identity, security and network on Account — all "who I am and what my device is doing". The log is evidence, not a preference.
  • · The config is about the app. Recording, retention, export and delete sit beside Storage in Settings — all "what this device keeps and for how long".
  • · Each cross-link carries state, not just a destination. "Recording on · keeping 90 days" and "1,284 events recorded" mean the common question is answered without navigating; the tap is for changing something.
  • · Back targets follow useAppNavigation.ts — viewer → Account, config → Settings, exactly as network-status → account works today. Two new entries in the back-target switch; no new navigation concept.
  • · The "recording off" empty state changed with the split — it can no longer offer a toggle it doesn't own, so it links to Settings instead. Worth noting as a real consequence, not a detail.

Deliberate choices worth challenging

  • · Width stays max-w-2xl (the settings/account column) rather than jumping to max-w-7xl. That constraint is what forces one line per event instead of a table — the sentence carries meaning, the meta line carries context. This is the first thing to revisit if you want a denser table view.
  • · Avatar, not per-kind icon tiles. Every row answers "who did what". Per-kind tiles would need ~30 new icons and read as noise at this width.
  • · Rows are not buttons. Most kinds have nothing to navigate to (the file may be gone, the space left). A row that sometimes does nothing is a false affordance — mockups.md anti-pattern.
  • · The filter triggers are the real ActionMenu primitive (widgets/ActionMenu.tsx) on its neutral trigger — the same react-aria dropdown behind "More" in Space View and the three-dot menu on ShareCard, wearing the documented secondary-button tokens. Three primary triggers side by side would read as three competing CTAs, which is why neutral was added instead of reaching for a raw <select> — that belongs to no part of the design system.
  • · No dividers between rows. Follows Settings.tsx (rows in one rounded-xl card, separated by hover). Density is raised to px-6 py-4 from the hub's p-6 — the one intentional scale-down.
  • · Badges only for exceptions. The status palette has five fixed meanings (design.md §7), so attribution tiers must not colonise it: bg-error-container = denied/failed outcome (its sanctioned meaning), bg-surface-container-highest = passive "Reported" for peer-claimed rows. First-party rows carry no badge.
  • · "Showing N events", never "N of M". A filtered total needs a full scan; the budgeted scan can return partial pages. Load-more is the honest affordance.
  • · Aggregation is visible in the copy. "shared the folder Brand Assets · 5,180 files · 12.4 GB" is one row — the no-firehose rule surfaced as a benefit rather than hidden. It is emitted by share.mounted (the deliberate act), not by the recurring folder reconcile, which produces no rows at all.
  • · The fourth category is "Security", not "App" (2026-08-04). App/device housekeeping — app updated, worker crashed, storage cleanup, download-folder changed, feedback sent — is not recorded: none of it answers "which user did what in a space". What remains in that bucket is exactly the security kinds (refused file request, integrity failure, creator divergence).
  • · No row implies a member was removed. There is no eject capability in the app, and the OR-Set membership model prevents adding one cheaply (approvals are grow-only, and the space content key is already handed out). Rows say "left the space" / "approved" — never "removed".
