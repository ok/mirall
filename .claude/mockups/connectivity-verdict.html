Connectivity verdict — mockup

UI delta for ~/Projects/Mirall/plans/plan-connectivity-verdict.md. Click the toggle to flip light/dark.

What's proposed vs. recreated

Proposed (the delta): a dedicated ConnectionProblem screen — its own title, its own purpose, and none of the space-management actions (§2, §3), shown in place of the spaces screen when the verdict is degraded and the user has no spaces; connectivity toasts for everything that arrives mid-session (§1, §5); a new onboarding check step (§6); and a reworked Network status screen — a plain-language Connection summary plus a savable diagnostics bundle, with the raw protocol fields demoted to an optional disclosure (§7, §7b). §1b is the timing evidence that picks screen over modal.
Recreated from code (baseline truth): the spaces screen header, filter chips and empty state from src/renderer/screens/SharedSpaces.tsx; the toast from components/toast/Toast.tsx (variant styles, countdown ring, action button); the onboarding shell from screens/Onboarding.tsx; the verdict panel, field rows and suggestion list from screens/NetworkStatus.tsx. Existing strings are the real locales/en/common.json values; everything under connectivity.* / networkCheck.* is marked proposed new copy.

Rejected: a persistent top banner, and a blocking modal

An earlier draft reused the UpdateBanner slot for connectivity errors. Rejected — the update banner stays for updates only and is not overloaded with error messaging. Errors go to the toast system; the standing explanation lives in the dedicated Connection problem screen. See §8a for the rejected treatment, kept so the decision stays legible.
Side benefit: --banner-h keeps its single owner, so the banner-stacking refactor in the plan (§9.2) is no longer needed.

A blocking modal was also considered and rejected — see §1b for the timing evidence and §8 for the treatment. Short version: we know the verdict before the user has acted, so there is nothing to interrupt; and blocking would be unjustified anyway, because creating a space works fine offline.

1b · When the verdict is actually available

This table decides the surface. Measured from the library sources, not assumed — dht-rpc emits 'ready' only after its bootstrap FIND_NODE walk finishes (index.js:395-404), and every response on that walk already fed _natAdd(). So NAT consensus exists at the same instant dhtReady flips.

Signal Gated on Typical
Tier 1 — NAT shape the bootstrap query, which already sampled it ~1–3 s — same moment as dhtReady
Tier 4 — canary stage 1 lookup, then a dial (10 s cap each) ~2–20 s
Tier 3 — transport health 4 ticks × TICK_INTERVAL 5000; cold until then ~20 s
Tier 2 — real peers having spaces, plus dials that actually failed 30 s – minutes

What follows

The decisive verdict for a brand-new user — Tier 1, optionally confirmed by the canary — lands before the user has done anything. That is the first frame of the app, not an interruption. A dedicated screen is therefore the right home for it, and no modal is needed: there is no context to seize.

The cases that arrive late — a network change mid-session, Tier 2 evidence, a VPN toggled after launch — are exactly the cases where seizing context would be wrong. Those get the toast. Fast ⇒ screen. Slow ⇒ toast. A modal is the one shape that is wrong for both.

7 · Network status — plain summary, with the detail in a file

Today the only route to any of this is a disclosure labelled "Address, NAT, DHT, counters", which then shows ~15 rows of raw protocol data — public IP, UDP ports, firewalled, randomized, ephemeral, routing-table size. An ordinary user can read none of it, and two of those NAT flags are misleading anyway.
Three deltas: a Connection summary in plain language that a user could read back over the phone; a Diagnostics card that saves the full detail as a file; and the raw fields demoted to a genuinely optional disclosure rather than being the only way in.

The redaction rule that makes this work: for connectivity debugging we need shapes, not identities. Whether host consensus formed, whether the port is 0, whether it changed over time, how many dials opened — none of that requires the actual IP, the real keys, or space names. So the default bundle answers every diagnostic question while carrying almost nothing identifying, and "remove identifying details" can stay checked for essentially every real support case.

The one genuinely new dependency: logs. logger.js writes to console only — nothing is ever persisted — and at default level it emits warn and error only. Main already taps every stream (worker stdout/stderr at main.js:741-747, its own console at installMainLogForwarding, and the renderer echo) but keeps none of it. A bounded ring buffer there is the whole feature — see the plan's Phase 10.

A11y: the preview is a real Modal — focus trapped, Escape closes, aria-modal with a labelled title. The <pre> is scrollable and keyboard-focusable so it can be read without a mouse. The two checkboxes are real inputs with real <label>s, not styled divs.

8 · Rejected alternatives not building these

Kept so the decisions stay legible. 8a reused the UpdateBanner slot for connectivity errors; 8b blocked the current screen with a modal.

8a · Persistent top banner

Mirall

Why rejected:
· The update banner is for updates. Overloading it with error messaging dilutes what it means and trains people to ignore it.
· Two banners stack, as shown, and both would fight over --banner-h — UpdateBanner is its sole owner today and resets it to 0px on unmount, so last-effect-wins would hide content under the fixed nav. Dropping this treatment removes the need for the BannerStack refactor entirely.
· A permanent bar is the wrong weight for something a user can act on once: it nags on every screen without ever explaining more.
Superseded by: §8b's rejection too — see below for why the modal went the same way.

8b · Blocking modal over the current screen

The shape suggested for the case where a user has already navigated into a space when the verdict lands.

Mirall

Project Aurora

Your network is blocking Mirall

Invites and shares won't arrive while this is the case.

Why rejected:
· The premise mostly doesn't hold. §1b: Tier 1 lands in ~1–3 s, at the same instant dhtReady flips, because dht-rpc emits 'ready' only after the bootstrap walk that already sampled the NAT. The user has not navigated anywhere yet — there is no context to seize.
· Where the premise does hold, seizing is exactly wrong. A verdict that arrives 30 s+ in (network change, Tier 2 evidence, VPN toggled) finds someone mid-task. Yanking them out of a space to announce something they cannot fix in the next five seconds is the classic interrupting-dialog antipattern.
· Blocking isn't justified. Creating a space works fine offline; only inviting and syncing fail. A modal that blocks access asserts a severity the situation doesn't have.
· No room to explain. The fix list is the actually useful content, and it doesn't fit a dialog without becoming a scrolling wall.
Chosen instead: fast ⇒ screen (§2, §3), slow ⇒ toast (§1, §5). The toast's action navigates to the same screen, so there is exactly one place the explanation lives.
