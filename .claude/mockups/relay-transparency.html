Relay transparency — mockup

UI delta for ~/Projects/Mirall/plans/plan-relay-transparency.md. Click the toggle to flip light/dark.

What's proposed vs. recreated

Proposed (the delta): one new row in the Connection summary (§1, §2); a new Relayed connections section grouped by relay, shown only while a relay is in use (§1); one extra counter in the Advanced → Relaying block (§3); and one new Activity Log kind, network.peer_relayed (§4). Everything hangs off a single new fact the worker reads from the socket — socket.relayed = { publicKey, adopted } — which hyperdht today computes and discards; the plan carries the six-line patch.
Recreated from code (baseline truth): screens/NetworkStatusScreen.tsx — PageHeader, VerdictBanner, Section / Field / MaskedField (label w-48, value text-accent, reveal + copy controls), the Advanced toggle; screens/DiagnosticsCard.tsx; the kind badge from settings/RelaySettingsSection.tsx; the row from components/activity/ActivityFeed.tsx. Existing strings are the real locales/en/common.json values; strings marked NEW in the note plates are proposed copy.

Rejected: live state in the Relay settings section, a relay glyph on member avatars, a "went direct" log row

Relay settings describes the relay this device offers; listing live peers there would imply the setting controls them, and an adopted relay has no setting at all. Live connection facts live on Network Status, next to the other live facts.
An avatar glyph would decorate every member row for a transient, benign state. hyperdht keeps hole-punching after the relay pairing and silently swaps the same socket to a direct path when the punch lands — a glyph would flicker. The per-peer state table in plan-pairwise-connectivity-diagnostics.md is the place for that later.
A network.peer_direct row was considered and dropped for this cut: the upgrade is silent and frequent and reads as churn. The relayed row is written only after a 10 s dwell, so a two-second bridge that went direct never appears.

1 · Network status — one own relay and one adopted relay in use

The macOS peer from the test setup: it offers an open relay in auto mode, two peers were paired through it, and a third connection was paired through a relay another peer offered. Two groups is the rare case, shown here only so both badge variants are visible in one frame. A device configures at most one relay, but hyperdht chooses the relay per connection: when both sides offer one, the accepting side's relay wins and the dialer adopts it (hyperdht/lib/server.js:636-644, lib/connect.js:782-790). So your relay can carry a peer that has none while a teammate's relay carries the connection to that teammate. Grouping by relay renders the normal case as a single group and the rare case without a special layout.

Reused verbatim: "Open relay" / "Private relay" and their badge classes from networkSettings.relays.kind.* + RelaySettingsSection.tsx; "Reveal" / "Hide" and the 30 s auto re-mask from MaskedField.

Why the adopted badge is passive grey: the adopting side cannot know whether the relay is open or private — the kind is not in the handshake payload — so the badge states the one fact we do have, who offered it. The bg-surface-container-highest text-on-surface-variant pair is design.md's "passive / role" token, which is exactly the register: a label, not a status. The own-relay badge keeps the kind because that side knows it.

a11y: the badge sits apart from the row it describes, so it carries an srLabel ("Relay: your relay, open relay" / "Relay: provided by Lena") and the visible pill is aria-hidden, the same pattern RowLane.tsx uses for file pills. Reveal and copy are named buttons. Nothing in this section is announced live — it changes when connections upgrade to direct, and a live region here would talk over the verdict banner's.

Grouping rule: one group per distinct relay key. "since" is shown only when a group has one person; with several it is dropped so the row stays a name list. A peer whose handshake has not landed yet shows its short key in place of a name, exactly as the Activity Log does.

The common case. The summary row says so in two words and the Relayed connections section is not rendered at all — an empty box would add a heading for nothing. With relay mode off the row reads "Off" instead.

3 · Advanced → Relaying — one added counter

The three existing counters come from hyperdht and move only on the accepting side of a handshake, so on a device that dials through a relay they read zero. The app already keeps its own dial-side count (stats.relaying.selected) and ships it in the frame; it is simply never rendered.
